# WP-036: Application — add an optional C ABI for Resource Type schema plugins

- **Status:** open
- **Phase:** Resource schema export — dynamic discovery
- **Priority:** P2
- **Difficulty:** hard
- **Blocked by:** [WP-031 / #31](https://github.com/ajare/willpower/issues/31), [WP-032 / #32](https://github.com/ajare/willpower/issues/32)
- **GitHub issue:** [#36](https://github.com/ajare/willpower/issues/36)

## Context

Some Resource Types are distributed independently and cannot be known when an application-specific bundle is generated. Resource-manifest tooling may optionally discover these through Resource Type Plugins. The plugin boundary must not expose `Resource`, `ResourceFactory`, C++ standard-library objects, or allocator ownership across compiler/runtime boundaries.

Native plugins are an optional adapter; Resource Schema Bundles remain the portable interchange format and should be preferred when dynamic discovery is unnecessary.

## Changes

- [ ] Define a minimal versioned C ABI through which a plugin returns a Resource Schema Bundle as bytes plus explicit size and lifetime rules.
- [ ] Define ABI negotiation, supported bundle versions, symbol names, error reporting, and plugin lifetime.
- [ ] Add cross-platform loading for explicitly supplied plugin paths; do not search or execute arbitrary libraries implicitly.
- [ ] Merge returned bundles through `ResourceSchemaCatalog` with the same collision and reference rules as file-based bundles.
- [ ] Keep plugin schema discovery independent from runtime `ResourceFactory` creation and application subsystem initialization.
- [ ] Add a sample plugin providing a custom Resource Type and specialized factory schema.
- [ ] Document trust, code-execution, architecture, dependency, and deployment implications.
- [ ] Add tests for incompatible ABI versions, missing symbols, malformed bundles, duplicate schemas, and unload/lifetime safety.

## Files

- `docs/`

## Acceptance criteria

- The schema tool loads a sample plugin and exports its custom schemas with the built-in catalog.
- The ABI header is consumable as C and exposes no C++ or third-party-library types.
- A plugin can be unloaded after its bundle bytes have been copied into the catalog.
- Incompatible or malformed plugins fail without corrupting the existing catalog.
- Plugins are loaded only from paths explicitly provided by the user or host application.
- Plugin tests pass on Windows and Linux.
