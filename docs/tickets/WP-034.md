# WP-034: Application — validate custom Resource Types from the runtime schema catalog

- **Status:** open
- **Phase:** Resource schema export — runtime integration
- **Priority:** P1
- **Difficulty:** hard
- **Blocked by:** [WP-032 / #32](https://github.com/ajare/willpower/issues/32)
- **GitHub issue:** [#34](https://github.com/ajare/willpower/issues/34)

## Context

Unknown custom Resource Types currently receive only common declaration validation. Even if a downstream application publishes a schema bundle, `ResourceLocation::scan()` cannot consume it because `ResourceManifestValidator` uses the private compile-time catalog and the root schema hard-codes built-in dispatch. Runtime validation must use the same catalog that applications and exporters can enumerate.

## Changes

- [ ] Allow an application to register a Resource Schema Bundle before Resource Locations are scanned.
- [ ] Define how `ResourceManager` owns or receives the catalog and how Resource Locations receive an immutable catalog snapshot.
- [ ] Initialize each application catalog with Willpower's built-in schemas.
- [ ] Refactor `ResourceManifestValidator` to resolve schemas through the catalog rather than directly through `embeddedResourceManifestSchemas()`.
- [ ] Validate the common Resource Manifest structure first, then dispatch each Resource declaration by Resource Type and each specialized Definition by factory type.
- [ ] Preserve existing atomic scan/rescan behavior and deterministic aggregate diagnostics.
- [ ] Reject schema registration after scanning starts, or define an explicit catalog replacement/rescan operation; do not allow scans to observe partial updates.
- [ ] Keep unknown Resource Types and unknown specialized factories on their documented generic validation paths.
- [ ] Test custom top-level and namespaced Resources, default and specialized factories, duplicate registrations, registration timing, and local-only reference resolution.

## Acceptance criteria

- A custom Resource declaration with a registered schema is rejected during `scan()` when structurally invalid and accepted when valid.
- Validation occurs before `StructuredData` conversion or publication of any `ResourceRecord`.
- A failed custom-schema rescan retains the last successful records.
- Default and specialized factory schemas dispatch according to `(resource type, factory type)`.
- Runtime schema resolution performs no network access.
- Existing manifests containing unregistered custom Resource Types remain backward compatible.
