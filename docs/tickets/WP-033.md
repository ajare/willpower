# WP-033: CMake — compose application-specific Resource Schema Bundles

- **Status:** open
- **Phase:** Resource schema export — downstream build integration
- **Priority:** P1
- **Difficulty:** hard
- **Blocked by:** [WP-031 / #31](https://github.com/ajare/willpower/issues/31)
- **GitHub issue:** [#33](https://github.com/ajare/willpower/issues/33)

## Context

External editors commonly expect one root schema, while the current `resource-manifest.schema.json` hard-codes the nine built-in Resource Types and excludes only those names from its permissive custom fallback. Downstream applications need build-system support to register their own schema files, merge them with Willpower's schemas, and generate a composed root that dispatches custom declarations correctly.

## Changes

- [ ] Add documented CMake functions for declaring a Resource Type schema with Resource Type, optional factory type, schema ID, and source file.
- [ ] Add a function that merges declared schemas with the built-in catalog and emits an application-specific bundle.
- [ ] Generate a deterministic application-specific root schema containing all registered Resource Type branches.
- [ ] Ensure the permissive unknown-type fallback excludes every registered Resource Type, not only Willpower built-ins.
- [ ] Generate specialized definition-factory dispatch for `(resource type, factory type)` while preserving default-factory fallback.
- [ ] Reject duplicate keys, duplicate schema IDs with differing content, invalid schema metadata, and incomplete `$ref` closure at configure/build time.
- [ ] Support build-tree use and installation of downstream bundles without requiring modifications to the Willpower source tree.
- [ ] Add a fixture downstream project that defines a custom `Resource` subclass and default and specialized definition schemas.

## Acceptance criteria

- A downstream CMake project can produce a self-contained bundle containing built-in and custom schemas.
- A standard Draft 7-aware YAML/JSON Schema tool validates custom Resource declarations through the generated root schema.
- Registered custom types do not pass through the unknown-type fallback.
- Specialized factory definitions select their matching schema; an unregistered specialized factory retains the documented generic fallback.
- Generation is incremental and reruns when any input schema or catalog metadata changes.
- The downstream fixture configures, builds, and tests on Windows and Linux.
