## Context

The load-time validator and all nine built-in Resource Type schemas need an end-to-end acceptance gate. The canonical schemas should also be discoverable by developers and usable by YAML-aware editors and the future Resource Manifest Editor.

## Changes

- [x] Add a table-driven regression suite covering every built-in Resource Type with valid and invalid Resource Manifests.
- [x] Cover malformed YAML separately from schema-invalid YAML.
- [x] Cover singleton/sequence compatibility, native/quoted scalar compatibility, default/specialized Definitions, unknown custom Resource Types, and local-only `$ref` resolution.
- [x] Verify aggregate diagnostics include stable file, Resource identity, instance-path, and source-position fragments.
- [x] Verify initial-scan and rescan atomicity end to end.
- [x] Verify schema validation runs before filesystem and cross-resource semantic validation.
- [x] Document schema locations, load-time behavior, diagnostics, supported compatibility forms, and the boundary between structural and semantic validation.
- [x] Add a repository YAML language-server association for `Resources.yaml` where it can consume the canonical manifest schema without changing production dependencies.
- [x] Run the full CMake/CTest suite on supported Windows and Linux toolchains.

## Acceptance criteria

- All nine built-in Resource subclasses have positive and negative load-time validation coverage.
- Invalid manifests never reach Resource instantiation or source-file loading.
- Runtime tests pass without schema files beside the executable and without network access.
- Documentation explains how to validate and fix a Resource Manifest.
- The complete CTest suite passes on Windows/MSVC and Linux/GCC or Clang.
