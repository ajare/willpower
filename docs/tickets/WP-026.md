# WP-026: Application — validate Resource Manifests atomically during scan and rescan

- **Status:** open
- **Phase:** Resource Manifest validation — loader integration
- **Priority:** P1
- **Difficulty:** hard
- **Blocked by:** [WP-025 / #25](https://github.com/ajare/willpower/issues/25)
- **Spec:** `docs/specifications/resource-manifest-schema-validation.md` §§6.4, 7, 9
- **GitHub issue:** [#26](https://github.com/ajare/willpower/issues/26)

## Context

`ResourceLocation::scan()` currently converts YAML immediately and populates `mNamespaces` incrementally. Structural errors can therefore survive until resource creation, and a failed rescan can discard or partially replace previously valid state. Validation must occur as part of loading the Resource Manifest, not as an optional later call.

## Changes

- [ ] Create Draft 7 schemas for the Resource Manifest envelope, common scalar definitions, and common Resource declarations.
- [ ] Support the existing singleton-or-sequence forms for Resource, Namespace, Option, Definition, and dependency collections.
- [ ] Reject unknown schema-owned fields, nulls, empty required identifiers, invalid names, and malformed dependency/definition shapes.
- [ ] Call `ResourceManifestValidator` inside `ResourceLocation::scan()` after YAML parsing and before `StructuredData` conversion.
- [ ] Build namespace/resource records in temporary storage and publish them only after parsing and structural validation succeed.
- [ ] Make `rescan()` preserve the last successfully scanned records when new content is invalid and allow a corrected retry.
- [ ] Keep filesystem, duplicate, dependency-resolution, and cycle checks in the existing semantic validation stages.
- [ ] Produce deterministic aggregate diagnostics containing the manifest path, instance path, Resource identity where known, and YAML line/column where available.
- [ ] Remove structural checks from later phases only when equivalent load-time coverage exists.

## Acceptance criteria

- Calling `scan()` alone rejects a schema-invalid Resource Manifest.
- Validation occurs before any `ResourceRecord` from that document is observable.
- A failed initial scan publishes no records.
- A failed rescan preserves records from the prior successful scan and can be retried after correction.
- Unknown custom Resource Types pass common declaration validation.
- Existing semantic validation still detects missing files, duplicate defaults, missing references, and cycles.
